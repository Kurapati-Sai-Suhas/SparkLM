# SparkLM — Production Deployment Runbook (M6)

Topology per the frozen architecture §15 (Phase B): **Neon** (Postgres + pgvector) ·
**Upstash** (Redis) · **Render** (Daphne ASGI web service) · **Vercel** (SPA).
Everything below is configuration — no code changes are part of a deploy.

The web tier is **torch-free** (§5): Render installs `requirements.txt` only.
SHAP explanations fall back to the heuristic explainer (identical response
schema); visual search degrades cleanly. Both return when the ML extras run
in a worker tier later (§15 Phase C).

---

## 1. Neon (database) — you do this once

1. Create a project at console.neon.tech (region close to Render's; e.g. `aws us-east-1` ↔ Render Oregon/Ohio — pick matching regions).
2. In the SQL editor run: `CREATE EXTENSION IF NOT EXISTS vector;`
3. Copy the **connection details** (host, database, user, password) from the dashboard.

**Data migration (existing local bank → Neon).** From the repo root, with
Docker Postgres running — paste your Neon connection string in place of
`$NEON_URL`:

```bash
docker exec learnlm_postgres pg_dump -U postgres -d learnlm_db \
  --no-owner --no-privileges | psql "$NEON_URL"
```

Notes:
- The dump carries the partitioned `groups_codesubmission` parent + members,
  all questions/boilerplate, users, and mastery state as-is.
- Re-running is destructive-free only on an empty database; to redo, drop and
  recreate the Neon database first.
- Afterwards, `python manage.py ensure_submission_partitions` runs on every
  service start (see render.yaml), keeping the partition horizon fresh.

## 2. Upstash (Redis) — you do this once

1. Create a Redis database at console.upstash.com (same region logic).
2. Copy the **TLS** connection URL (`rediss://default:<password>@<host>:6379`).
   Django's cache, DRF throttles, and the Channels layer all pick it up from
   the single `REDIS_URL` variable.

## 3. Render (backend) — blueprint deploy

1. Push to GitHub (the repo root contains `render.yaml`).
2. Render dashboard → **New → Blueprint** → select the SparkLM repo. Render
   reads `render.yaml` and creates the `sparklm-api` web service.
3. Fill in the `sync: false` variables in the service's **Environment** tab:

| Variable | Value |
|---|---|
| `POSTGRES_DB` / `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_HOST` | from Neon (host like `ep-xxx.aws.neon.tech`) |
| `REDIS_URL` | the Upstash `rediss://…` URL |
| `CORS_ALLOWED_ORIGINS` | your Vercel origin, e.g. `https://sparklm.vercel.app` (comma-separate extras) |
| `JUDGE0_API_KEY` / `JUDGE0_API_HOST` | your RapidAPI values |
| `GROQ_API_KEY` / `GEMINI_API_KEY` | your LLM keys |
| `N8N_WEBHOOK_URL` | optional (coach falls back without it) |

   `SECRET_KEY` is auto-generated by the blueprint; `DJANGO_DEBUG=false`,
   `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, `DRF_NUM_PROXIES=1` (Render runs
   one proxy hop), and `ENABLE_SHAP_XAI=false` are preset. If Render assigns
   a different service name, update `DJANGO_ALLOWED_HOSTS` and
   `CSRF_TRUSTED_ORIGINS` to match the real `*.onrender.com` domain.
4. Deploy. Watch for: `collectstatic` in the build, `migrate` +
   `ensure_submission_partitions` in startup, then Daphne listening. Render
   flips the service live when `/healthz` returns 200 (it checks the DB).

Operational notes:
- **Free-tier sleep:** the instance idles after ~15 min without traffic; the
  first request then takes ~30–60 s. Before a demo, open the URL once.
- **Model artifacts** load once per process — after `retrain_ai`, redeploy or
  restart the service (deliberate: no hot-swap past the §5 evaluation gate).
- Content commands (reseed/backfill) are cheapest run locally against Neon:
  set the `POSTGRES_*` vars in a shell and run the command as usual.

## 4. Vercel (frontend) — you do this once

1. vercel.com → **Add New Project** → import the repo.
2. **Root Directory:** `studysphere-ai-11` (it auto-detects Vite; the SPA
   rewrite lives in `vercel.json`).
3. Environment variables (build-time):

| Variable | Value |
|---|---|
| `VITE_API_URL` | `https://sparklm-api.onrender.com` |
| `VITE_WS_URL` | `wss://sparklm-api.onrender.com` |

4. Deploy, then put the resulting origin into Render's
   `CORS_ALLOWED_ORIGINS` (step 3) if it differs.

## 5. Smoke checklist (live URL)

1. `GET https://sparklm-api.onrender.com/healthz` → `{"status": "ok"}`.
2. Admin loads **with CSS** at `/admin/` and login works (CSRF trusted origin).
3. SPA: register/login → JWT issued (auth throttle counts via Upstash).
4. Coding Hub: next-problem returns a question with `sample_case` + XAI
   payload (heuristic path), **never** hidden test cases.
5. Run + Submit a known-good Python solution → Judge0 verdict, Elo update.
6. Learning Path renders the DAG with real mastery data.
7. Group chat over `wss://` (Channels via Upstash layer).
8. `python manage.py check --deploy` locally with prod-like env for the
   security checklist (HSTS warnings are acceptable on Render's TLS).

## Observability (M8)

- **Sentry:** create a free project at sentry.io (platform: Django), copy its
  DSN into the Render env var `SENTRY_DSN`, save (auto-restarts). Every
  unhandled production exception then arrives with a stack trace. Without a
  DSN the integration is a complete no-op.
- **Access log:** every API request logs one line (`method path -> status (ms)`)
  to the Render log tail; `/healthz` probes are excluded to keep it readable.

## Backups (M8)

Primary: **Neon point-in-time restore** (console → Backup & Restore) — the
free tier keeps a restore window; use it for disaster recovery.
Belt-and-suspenders: `scripts/backup_prod.sh` takes an explicit local
`pg_dump` snapshot (run it before demos or risky data operations; keep the
output out of git). Pre-demo runbook: snapshot + open the live URL 10
minutes early.

## Rollback

Render → the service's **Deploys** tab → "Rollback" to the previous image.
Database rollbacks: restore from Neon's point-in-time restore (free tier
keeps a history window) — never `migrate` backwards in production.
