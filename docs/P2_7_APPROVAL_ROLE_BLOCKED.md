## B. Exact privilege scope

```sql
CREATE ROLE learnlm_approve_rw LOGIN PASSWORD '…'
    NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS NOINHERIT;

GRANT CONNECT ON DATABASE neondb                  TO learnlm_approve_rw;
GRANT USAGE   ON SCHEMA public                    TO learnlm_approve_rw;
GRANT SELECT  ON groups_question                  TO learnlm_approve_rw;
GRANT SELECT  ON groups_referencesolution         TO learnlm_approve_rw;
GRANT SELECT  ON groups_oracleexecution           TO learnlm_approve_rw;
GRANT SELECT (id) ON groups_user                  TO learnlm_approve_rw;
GRANT SELECT, INSERT ON groups_questionapproval   TO learnlm_approve_rw;
```

Every line traced to the code that needs it, as the brief required:

| grant | why the approval path needs it |
|---|---|
| `groups_question` SELECT | `resolve_question`, read through the alias |
| `groups_referencesolution` SELECT | `canonical_reference`, via the question's related manager, which inherits the alias |
| `groups_oracleexecution` SELECT | `collect_case_evidence` and `_execution_provenance` — the evidence the digest is computed from |
| `groups_user (id)` SELECT | Django validates FK existence in `full_clean` through the object's own connection, issuing `SELECT 1 … WHERE id = %s`. Column-scoped, so the role cannot read an email or a password hash |
| `groups_questionapproval` INSERT | the one row it writes |
| `groups_questionapproval` SELECT | PostgreSQL requires it for the `RETURNING id` Django uses to populate the pk, and the duplicate check reads existing approvals |

**Two grants that are NOT there, and why:**

- `groups_questionapproval_id_seq` was in my first draft, on the assumption the
  pk is a `bigserial`. It is `GENERATED BY DEFAULT AS IDENTITY`
  (`pg_attribute.attidentity = 'd'`), whose sequence is owned by the table and
  needs no privilege. The minimality test proved the grant does nothing, so it
  came out rather than staying in "to be safe".
- Anything on `groups_question` beyond SELECT. `APPROVAL_FORBIDDEN` refuses a
  role that holds INSERT/UPDATE/DELETE on it, so an over-granted approver is
  rejected rather than used. Same for UPDATE/DELETE on the approval table and
  any write on the reference or the executions.

**This is proved, not asserted.** `test_the_documented_grant_list_is_sufficient`
opens a **real second connection** logged in as a role built from exactly this
list and runs the real command through it; the parametrised
`test_every_documented_grant_is_necessary` drops one line at a time and requires
each drop to break the approval.

I tried `SET ROLE` on the shared test connection first. It is wrong: it also
applies the role to the operator lookup, which in production runs on `default`
as the read-only census role. That simulation demanded SELECT on the whole of
`groups_user` — password hashes included — from a role whose entire purpose is
to insert one row, and it tested a deployment that does not exist.

## D. What `question_approve` actually checks

Read from the code, in the order it runs:

1. operator exists, is active, is staff (`resolve_operator`)
2. which database this is (`describe_target`)
3. on production: role ∈ `{learnlm_approve_rw}`; privileges ⊇ `APPROVAL_PROBE`;
   privileges ∩ `APPROVAL_FORBIDDEN` = ∅
4. `--confirm` present
5. the question exists, read through the alias
6. a canonical reference exists — approved, active, unmodified since approval
7. every artifact blocker: no oracle evidence, fewer than two agreeing runs,
   conflicting outputs, a nondeterministic execution on record, a legacy
   expected output, an unknown contract, **a failing quality gate**
8. the supplied digest equals a freshly recomputed one
9. **no existing approval already records this exact digest** (new, see below)

It does **not** require the question to leave `DRAFT`. That requirement belongs
to `question_promote` (its gate 7, backed by a DB CHECK). So:

> **The brief asked what status transition approval requires. The answer is
> none.** Approving a DRAFT is intentional — an approval is a statement about an
> artifact, and the artifact is what it is regardless of status. `q3309` will
> still need its status advanced before promotion, which is a separate decision
> for the promotion phase.

**One place where the brief and the existing lifecycle disagreed.** The brief
requires "approval not already present". The model is explicitly append-only —
"superseding is expressed by recording a NEW approval; `current_for` reads the
latest" — so refusing whenever any approval exists would break the documented
way to re-approve a changed artifact. I implemented the version that satisfies
the intent without breaking the design: **an approval is refused when one
already records the same `artifact_digest`**, since that row would add no
evidence and is exactly what an accidental re-run produces. A *changed* artifact
may still supersede. Both behaviours are tested.

## F. A defect found while inspecting the lifecycle

The artifact read the question through the operator alias and its **oracle
evidence through `default`** — one digest, assembled from two databases. On
this deployment both point at the same Neon instance so it is invisible; on one
where they differ it is undetectable in the digest, which is worse.

Fixed: `collect_case_evidence` and `build_artifact` take `using`, defaulting to
`question._state.db`, and all three commands pass their alias explicitly.
`QuestionApproval.current_for` was reading on `default` too, and now reads on
the question's connection. This is what determined the grant list — it is why
`groups_oracleexecution` SELECT is on it.
