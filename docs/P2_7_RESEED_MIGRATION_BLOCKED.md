# P2.7h-15 — Reseed migration verified, production apply BLOCKED on DDL

**Phase 2 of the reseed implementation.** Everything the brief asked for was
built, checked and mutation-tested. The one step that could not be completed is
the production apply itself, and the reason is a missing privilege, not a
missing decision.

---

## 1. The blocker, stated first

No credential available to this workspace can create a table on production.

```
role                       CREATE on schema public
learnlm_approve_rw         False
learnlm_boilerplate_rw     False
learnlm_census_ro          False
learnlm_contract_rw        False
learnlm_hidden_test_rw     False
learnlm_oracle_rw          False
learnlm_pilot_rw           False
learnlm_preimage_rw        False
learnlm_promote_rw         False
learnlm_remediate_rw       False
learnlm_status_rw          False
neondb_owner               True     <-- not present in .env
```

`groups_question` is owned by `neondb_owner`. Every `learnlm_*` role is a
column-scoped DML role by construction; none was ever granted DDL, which is
correct and was the point of the ten-role design. Migration 0048 contains a
real `CREATE TABLE`, so it cannot be applied by any of them.

`.env` carries no owner entry, there is no `~/.pgpass`, no `DATABASE_URL`, and
no owner credential anywhere in the backend tree. The `neondb_owner` string does
appear in four Python files — all of them forbidden-role assertions in gate
tests, not credentials.

**This is the correct failure.** A workspace that could apply arbitrary DDL to
production would defeat the privilege separation the last several phases were
spent building. The apply is an owner action, and the owner is you.

## 2. Migration dependency chain

```
0046_suite_expansion_action_class      [applied on production]
        │
        ▼
0047_status_transition_action_class    [NOT applied]
        │
        ▼
0048_reseed_action_classes_and_ledger  [NOT applied]
```

`manage.py migrate --plan`, read against production:

```
groups.0047_status_transition_action_class
    Alter field action_class on remediationaction
groups.0048_reseed_action_classes_and_ledger
    Alter field action_class on remediationaction
    Create model ReseedLedger
```

Exactly two migrations, in this app only. Nothing from another app rides along.

### Is 0047 required?

**Yes — required, and it must not be faked.**

Its *schema* effect is nil. `sqlmigrate groups 0047` emits:

```sql
BEGIN;
--
-- Alter field action_class on remediationaction
--
-- (no-op)
COMMIT;
```

The column is a bare `varchar(32)` with no CHECK constraint, so Django `choices`
never reach the database. That is why four `STATUS_TRANSITION` rows wrote
successfully on production while 0047 sat unapplied.

But 0048 declares `dependencies = [('groups', '0047_...')]`, and Django will not
apply a migration whose dependency is unrecorded. The row in `django_migrations`
is the requirement, not the SQL.

Faking it (`--fake`) would produce the same database and the same recorded
history here, since the SQL is genuinely empty — but it establishes a habit of
deciding per-migration whether history may be skipped, and that judgement is
wrong exactly once. Applying it normally costs nothing: an empty transaction and
one history row. **Apply it, do not fake it.**

A mutation confirmed this is load-bearing: rewriting 0048's dependency to point
at 0046 directly (P4) was killed — two leaf nodes in one app makes Django refuse
to build the graph at all.

## 3. Exact schema effect

`AlterField` on `action_class` is a no-op in both migrations. The entire real
effect of reaching 0048 is one table:

```sql
CREATE TABLE "groups_reseedledger" (
    "id"          bigint NOT NULL PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    "stage"       varchar(24) NOT NULL,
    "last_error"  text NOT NULL,
    "attempts"    integer NOT NULL CHECK ("attempts" >= 0),
    "created_at"  timestamp with time zone NOT NULL,
    "updated_at"  timestamp with time zone NOT NULL,
    "batch_id"    bigint NOT NULL,
    "question_id" bigint NOT NULL,
    CONSTRAINT "reseed_ledger_one_per_question_per_batch"
        UNIQUE ("batch_id", "question_id")
);
ALTER TABLE "groups_reseedledger" ADD CONSTRAINT
    "groups_reseedledger_batch_id_37096568_fk_groups_re"
    FOREIGN KEY ("batch_id") REFERENCES "groups_remediationbatch" ("id")
    DEFERRABLE INITIALLY DEFERRED;
ALTER TABLE "groups_reseedledger" ADD CONSTRAINT
    "groups_reseedledger_question_id_e4f65b45_fk_groups_question_id"
    FOREIGN KEY ("question_id") REFERENCES "groups_question" ("id")
    DEFERRABLE INITIALLY DEFERRED;
CREATE INDEX "groups_reseedledger_batch_id_37096568"    ON "groups_reseedledger" ("batch_id");
CREATE INDEX "groups_reseedledger_question_id_e4f65b45" ON "groups_reseedledger" ("question_id");
CREATE INDEX "reseed_ledger_batch_stage_idx"            ON "groups_reseedledger" ("batch_id", "stage");
```

Additive in the strict sense: no `ALTER` against an existing table, no `UPDATE`,
no `DELETE`, no data migration, no `RunPython`. No existing `Question` or
`RemediationAction` row is read or written. No trust, serving or grading column
is introduced anywhere.

## 5. Foreign-key behaviour

Both FKs are emitted as `confdeltype = 'a'` — NO ACTION, deferrable, initially
deferred. So the database alone guarantees only that a ledger row cannot be
orphaned; `on_delete=PROTECT` is what turns that into a clean application-level
refusal.

Worth stating plainly, because it is a new coupling: **the ledger holds a veto
over deleting a question.** A question with a ledger row cannot be deleted
through the ORM. That is deliberate — an orchestration record must not outlive
its subject — but it did not exist before, so it is asserted rather than assumed.
The veto runs one way only: deleting a ledger row leaves its question and batch
untouched, digest unchanged.

Four tests were added for this (STEP 5 asked for FK behaviour, and the Phase 1
suite had no coverage of it). One of them documents a subtlety: because the FKs
are `INITIALLY DEFERRED`, a bad reference is not rejected by the `INSERT` but at
`COMMIT`, which never arrives inside a rolled-back test transaction. The test
forces `connection.check_constraints()` rather than skipping the case.

## 6. Applying it — the procedure

Run from `LearnLM/backend/LearnLM`, as the owner, supplying the password in your
shell without echoing it:

```
POSTGRES_USER=neondb_owner POSTGRES_PASSWORD=<owner password> \
    ../.venv/Scripts/python.exe manage.py migrate groups 0048
```

`settings.py` reads `POSTGRES_*` via `os.getenv`, and `load_dotenv()` defaults to
`override=False`, so the shell values win over `.env` for that one command.

Expected output — two migrations, nothing else:

```
Applying groups.0047_status_transition_action_class... OK
Applying groups.0048_reseed_action_classes_and_ledger... OK
```

### Least privilege

There is no lower-privileged mechanism available. `CREATE TABLE` in schema
`public` requires either the owner or a role granted CREATE on that schema — and
creating such a role is itself an owner action. Using the owner for a one-off
DDL and granting nothing afterwards leaves **no new standing privilege**, which
is the least-privilege outcome here.

Deliberately **not** included: any `GRANT` on `groups_reseedledger`. No
orchestrator exists yet. Until a future phase grants it, the table is
unwritable by every `learnlm_*` role — which is the correct resting state.

### One thing the apply does silently

Production carries an `ALTER DEFAULT PRIVILEGES` rule:

```
neondb_owner  →  tables  →  learnlm_census_ro = SELECT
```

So the moment the owner creates `groups_reseedledger`, the application's
read-only role **automatically gains SELECT on it**, with nobody granting
anything. No `INSERT`/`UPDATE` is auto-granted, so the ledger still cannot be
written by any application role.

Read access is not authority — no trust or serving module imports the ledger,
and a test asserts that. But the grant is automatic and unrequested, so it is
recorded here rather than discovered later.

## 10. Unexpected findings

**a. `learnlm_pilot_rw` exists on production and is completely dormant.**
The role can log in, `PILOT_*` credentials sit in `.env`, and `settings.py`
defines no `pilot` alias. It holds **zero table grants** and no column privilege
on `groups_question`. Not a hole — a role with no privileges can do nothing —
but it is a live credential for an empty role, and I did not create it.

**b. `STATUS_*` is duplicated in `.env`.** Every one of `STATUS_DB`,
`STATUS_HOST`, `STATUS_PASSWORD`, `STATUS_PORT`, `STATUS_USER` appears twice.
`load_dotenv` takes the last occurrence, so the file's behaviour depends on
ordering rather than intent. Worth reconciling.

**c. A real test-isolation defect, found by the full regression.**
`common/test_python_runtime.py` calls `importlib.reload(common.languages)` to
exercise the `JUDGE0_PYTHON_LANGUAGE_ID` override. Its teardown reloaded the
module to restore correct *values* — but `reload` rebinds every module-level
name to a **new object**, while `groups.coding_views`, which did
`from common.languages import LANGUAGE_IDS`, still held the old dict.

The result was two equal-but-distinct language registries in one process, which
is precisely the duplicate-mapping split that
`test_judge0_language_ids_come_from_the_one_registry` exists to forbid — the
test that caught three production spelling-drift bugs. It failed for every test
running after that file.

Fixed by restoring the original objects **by identity**, refilling the dicts in
place instead of replacing them. This is my defect, introduced during the
runtime-switch phase; the invariant was not weakened to accommodate it.

**d. `LearnLM/scripts/test_judge*.py` break a bare `pytest` run.**
Three ad-hoc Judge0 scripts dated 2026-07-04 match `test_*.py` and touch the
database at import time with no `django_db` marker, so they abort collection with
`RuntimeError: Database access not allowed`. They can never pass under pytest and
reference nothing from this milestone. Regression is therefore run with
`--ignore=scripts`. Renaming them out of pytest's path would remove the trap.
